RUN-001 は「落ちる」側の話で、**配信の数字を1つも持っていない**。`harness.mjs` が出すのはビルド時間であって、
format A が要求する cold/warm（配信の初回バイト）ではない。EP02〜04 が queue で `BLOCKED_RUN` のまま

## 3. cold の定義を言い換えた（ここは正直に書く）

`bench/README.md` のルール2は cold を「**キャッシュパージ後**の初回バイト」と書いている。
`*.pages.dev` は Cloudflare 自身のゾーンで、**こちらからパージする手段が無い**。
そこで RUN-002 の cold は次の意味で使う。

> デプロイが到達可能になった直後、**まだ誰もリクエストしていないデプロイ固有URL**への初回リクエスト。

エッジのキャッシュを空にした状態ではない。ルール2の文言はこの run では厳密には満たせていないので、
数字を「パージ後」と言い換えて出すことはしない。独自ドメインを Cloudflare に載せれば purge API が使えるので、
そちらへ移した時点でルール2どおりの cold を測り直す。

## 4. 途中で踏んだもの（次に同じ罠を踏まないため）

**1周目の TTFB が全部 `http=000 / 0ms` で返ってきた。** 原因はサイトでもネットワークでもなく2つ。

1. **新しい Pages プロジェクトの `*.<project>.pages.dev` ワイルドカード証明書は非同期に発行される。**
   apex（`<project>.pages.dev`）は先に立つが、デプロイ固有URLは証明書が出るまで TLS ハンドシェイクで落ちる。
   同じ日に20分早く作った `deploy-bench` の固有URLは通り、5分前に作った `deploy-bench-ep02` は通らなかった＝
   プロジェクトの新しさの問題だと切り分けられた
2. **`curl`（システムの LibreSSL）はその失敗を `http_code=000` / `time_starttransfer=0` に潰す。**
   「0ms で返ってきた」ように見えるので、そのまま記録すると**世界最速の TTFB を捏造する**ところだった

ハーネスを node の `fetch` に替え（エラーが握り潰されず TLS の内容が出る）、
証明書が出て 200 が返るまで待ってから測るようにした。2周目は待ち 844ms で立ち、そのまま計測できている。

## 5. この run が満たしていないもの（正直に）

- **cold はパージ後ではない**（§3）
- **他ホストとの比較になっていない。** 測ったのは Cloudflare Pages ただ1つ。WP Engine・Kinsta・Cloudways は
  有料アカウントが要る（P0-11）ので、queue に数字も評価も付いていない
- **TTFB は青森の1拠点から5本**。地理分散も時間帯分散もしていない。中央値 33ms は「この回線からこのエッジまで」の数字
- **ページが小さい。** `create-next-app` の初期ページ1枚（`/` と `/_not-found` の2ルート）。
  実案件のサイトで同じ数字が出る保証はない
- **ビルド時間は Turbopack 込みの `next build` 全体**。書き出しだけを切り出していない
